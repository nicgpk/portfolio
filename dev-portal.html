A fragmented platform made service creation slow.

Agoda’s internal developer platform was fragmented, slow and unscored. Creating a service took 1–2 working days; deploying to private cloud meant Slack and tribal knowledge. Home was a flat directory of links. Engineers could not find critical paths, and leadership had no System Usability Scale (SUS) baseline to measure whether design helped.

My role

As Senior Product Designer in Agoda Engineering and the first designer in DevOps, I led 0-to-1 design for Developer Portal and Deployment, including domain research, information architecture, interaction and visual design.

Design goals

  • Make developer experience measurable.
  • Support migration from servers to private cloud.
  • Make critical work easier to find.
Before
Service creation took 1–2 working days, without a usability baseline.
The design response
Task-based navigation, a searchable catalog, in-context guidance and a staged deployment workflow.

Learn the domain. Make the friction measurable.

I combined developer interviews, technical domain learning and a heuristic review to make the work measurable.

The synthesis exposed recurring needs for incremental rollout control, recovery guidance when permissions or terminology blocked progress, and continuity as rotating release managers returned to infrequent workflows.

  1. Domain immersion

    Interviewed 15+ developers and learned Kubernetes, Docker and CI/CD to understand their work.

  2. Heuristic evaluation

    Assessed the platform against Nielsen’s heuristics and documented 47 usability issues.

  3. Baseline & measure

    Established a SUS baseline of 61.9 and repeated the measure every two quarters.

  4. Ideation & phased delivery

    Phase 1: quick wins to unblock developers. Phase 2: fuller automation and approval workflows.

Organize around the work engineers need to do.

Replace the flat link directory with task domains and a searchable catalog: structure developers can learn and the team can measure. Manage, Plan, Build, Secure and Monitor map the development lifecycle; FAQ keeps supporting documentation accessible.

The home page connects services, databases, ownership and integrations; team OKRs; testing and versioning; security; and post-deployment monitoring. Quick links and help stay close to the work.

Static product examples. Names, records and configuration values are illustrative.

A catalog with ownership and source in view.

The component catalog brings owner, manager, booking impact, source and last commit into one table. My components and All components, alongside label and ownership filters, make this source of truth easier to navigate.

Turn a maze into a guided path.

Service creation bundled repository setup, ownership and tags into one dense wizard. Missing admin groups required offline Active Directory (AD) requests. Unclear platform and system tags created ownership problems, and developers left the flow to find documentation or ask for help.

The response separated guidance that could unblock developers while engineering addressed the automation backlog from deeper changes to ownership, tagging and approval workflows.

Phase 1: provide guidance.

  • Skip repository setup when it is not needed.
  • Provide documentation at important bottlenecks.
  • Allow leave and resume when requests take time.
  • Surface top-used pages and quick links on home.

Phase 2: streamline the experience.

  • Rethink ownership and remove requirements where unnecessary.
  • Reconsider tags developers did not know how to apply.
  • Work toward automation and approval workflows beyond immediate fixes.

Make deployment a reviewable decision.

Give developers a productized deployment path and a clear way to move legacy services from servers to private cloud. Environment, Rollout and Review separate configuration, rollout decisions and final confirmation.

1. Configure the environment.

Group environment name and cluster pool, Docker repository and image tag, healthchecks, and CPU and memory requests. Readiness guidance explains startup and liveness probes alongside container configuration.

2. Control the rollout.

Canary and Rolling update make the strategy explicit. The canary example progresses through 10%, 20% and 30%, with replica counts and ordering per data center. Monitoring connects the deployment to Slack, a 300-second ramp-up and a 900-second monitoring period.

3. Inspect the full configuration.

Review brings repository, image, resources, readiness, rollout strategy, monitoring and targets together before deployment.

Keep the service and its critical actions together.

Restructure information so developers see important work first: clear hierarchy, less noise and critical paths that are easy to find. Service detail brings environments, monitoring and deployment into one place, supported by Catalog, Deployment, Integrations and Security navigation.

Environment, cluster pool, image version, pod health, updater and status sit in one table. Desired, In progress, Pending and Error make the operational state visible. Monitoring, Quick Deploy and New Environment stay close to the service.
